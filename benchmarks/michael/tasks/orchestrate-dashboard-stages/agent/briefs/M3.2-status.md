# M3.2: Status taxonomy + derivation (`src/status.ts`) (excerpt)

> Dependencies (merged): M3.1 (`src/plan-parser.ts`) and M2.3
> (`src/github.ts`). Consume both as-is; do not edit either.

## Goal
Map a plan stage's associated PRs / issues / blocks to exactly one of the
AC-005 statuses — `planned`, `dispatched`, `in-review`, `blocked`,
`needs-attestation`, `needs-human-test`, `merged`. Pure module — it operates
over data it is handed.

## Design
1. `StageStatus` = the seven AC-005 values exactly; document the precedence in
   the module header.
2. `deriveStageStatus(input)` — a pure function over a per-stage bundle
   `{ prs, issues, blocks, reviewsByPr?: Map<number, ReviewData[]> }`:
   - open block(s) present → `blocked`
   - `agent:needs-attestation` / `agent:needs-human-test` label →
     `needs-attestation` / `needs-human-test`
   - an associated PR with review activity (via `reviewsByPr`) → `in-review`
   - an `agent:go`-assigned issue with an open PR but no review yet → `dispatched`
   - a merged PR for the stage → `merged` (see the merged-data gap below)
   - none of the above → `planned`
3. Stage→work linkage is injectable. A stage links to issues/PRs by a
   convention (the task id — e.g. `M3.2` — appearing in the issue/PR title).
   Take a matcher with a sensible default. Optionally export
   `deriveStatuses(graph, input)` over the whole graph.
4. Multi-repo aggregation (AC-016): a stage may match work across several
   repos; aggregate to the highest-precedence status.

## Merged-data gap
`github.ts` exposes `listOpenPRs` only and `PullRequestData` has no
`merged_at` field — there is no read path for merged PRs. Implement the
`merged` branch over whatever PR data the function is given. Do not widen
`github.ts` in this slice; live merged detection wires up when a later slice
adds a closed/merged-PR read path.
